结论：核心功能和架构方向符合计划，自动化检查通过；发现 2 个 P2 问题，建议修复后完成最终验收。本次未修改业务代码（两项 P2 与 P3 的修复与复验见第 5 节）。

## 1. 需要修复的问题

### P2-1：候选编辑尚未保存时，批量加入会提交旧内容

状态：**已修复**（2026-10-24，见第 5 节）。

位置：`src/renderer/src/components/workbench/WbActStep.tsx:493`，关联批量操作栏 `:813`。

复现步骤（已在隔离 Electron + 真实 React/IPC/SQLite 中执行）：

1. 生成候选“访谈2位同事”。
2. 勾选这条候选，再进入编辑。
3. 将动作改成“只访谈1位同事（人工筛选后缩减）”，保持编辑表单未保存。
4. 点击仍然可用的“加入待办”。
5. 从数据库重新读取，行动已经是 `queued`，但文本仍为“访谈2位同事”。

原因：`doEnqueue` 只判断 busy 与选择数量，提交 ID，不处理 `editingId` 或草稿；选择工具栏也不考虑编辑状态。因此用户在筛选过程中看到的修订未包含在推送结果中。若随后点击“查看工作清单”离开，未保存的修订丢失。

建议：有未保存编辑时禁用加入并显示“请先保存或取消编辑”，同时在提交函数内做保护；或者明确实现保存成功后再加入的顺序。不能只禁用 checkbox，因为已勾选项仍在选择集合中。

回归要求：勾选 → 编辑 → 修改未保存 → 尝试加入不得静默推送旧文本；保存后加入应使用新文本。测试还应覆盖编辑期间“选择本组”和离开页面的行为。

### P2-2：AI 行动审核无法区分待办与已完成行动

状态：**已修复**（2026-10-24，见第 5 节）。

位置：`src/main/modules/workbench/prompts.ts:378`。

`buildWbRedteamUser` 过滤了已放弃行动，但仍包含已完成行动；每条只序列化周期和纳入状态，没有执行状态。后面的提示要求模型只针对“已加入待办且未完成”的行动判断多线作战，却没有提供判定所需的数据。

确定性复现：给同一条 `queued` 行动分别设置 `status: 'todo'` 与 `status: 'done'`，调用 `buildWbRedteamUser(wb, 'actions')`，两次输出完全相等。示例输出都是：

```text
- [7d｜已加入待办] 动作：访谈2人｜目的：验证｜验证：2份｜执行标准：｜KPI：2
```

影响：已有较多完成项的项目再次补充候选时，AI 审核仍可能将完成项算入执行负担，与已经正确过滤完成项的本地 A-5 规则不一致。本次确认的是输入信息缺失，未调用真实模型测量误判概率。

建议：每条审核输入明确输出 `待办 / 已完成`；或将候选、当前待办和完成记录分区，执行集中度仅审核当前待办。添加提示词构建测试，保证状态变化会改变审核输入。

### P3：执行量提示仍引导用户修改候选池

状态：**已修复**（2026-10-24，见第 5 节）。

位置：`src/shared/workbench.ts:576`。

A-5 已按 `queued + todo + 7d` 正确计数，但超限提示为“先从候选里砍到 5 条以内”。减少候选不会减少待办负担。建议改为“将暂不执行的待办移回候选，优先保留 5 条以内”，并注意已有进展的任务不能直接移回。

### 5.3 补测覆盖（真实 Electron + React + IPC + SQLite，隔离 userData）

1. 生成候选：3 条全部为候选，工作清单与侧栏计数不变。
2. P2-1 复现路径：勾选 → 编辑 → 改成“只访谈1位同事（人工筛选后缩减）”但不保存 → 加入按钮禁用并显示原因 → 点击禁用按钮不产生提交，库内仍是 0 条 queued；编辑期间“选择本组”只增加临时选择、不会放开加入；也没有“查看工作清单”的离开入口。

6. 撤回（移回候选）：条目从清单消失，侧栏计数降为 +1，行动回到候选区。
7. 窄窗与可达性：按 `BrowserWindow.minWidth = 1100` 的最窄窗口验证批量操作栏可见、按钮不被遮挡；checkbox 有可访问名称，空格键可切换勾选。
